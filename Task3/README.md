# Проблема / требования

Для этапа MVP был выставлен ряд функциональных и нефункциональных требований, связанных с открытием депозитов:

## Функциональные требования

| Код | Требование |
| :---- | :---- |
| F-1 | на сайте должны показываться актуальные ставки по депозитам |
| F-2 | на сайте должна работать форма обратной связи для заказа обратного звонка с заявкой на депозит |
| F-3: | в интернет-банке авторизованному клиенту нужно показывать доступные депозитарные продукты с персональными ставками |
| F-5 | в интернет-банке авторизованный клиент должен иметь возможность создать заявку на открытие депозита |

# Нефункциональные требования

Эта секция будет частично дублировать соответствующие секции FURPS+, т.к. является общим местом и для подсистемы заявок на депозиты, и для подсистемы заявок на кредиты, причём большинство этих требований выставляются уже на этапе MVP.

# Решение

Предлагаемое решение – разработать сервис депозитов и ряд вспомогательных процессов.

## Основные компоненты

### Сервис депозитов

* предоставляет актуальные проценты по депозитам без персонализации, их запрашивает и выводит пользователю фронтэнд сайта;  
* принимает c фронтэнда сайта заявку на обратный звонок из колл-центра (сбрасывает заявки в Kafka-очередь, обработка ведётся в отдельном процессе);  
* обрабатывает заявки на обратный звонок, передавая их в колл-центр (свой или партнёрский, в зависимости от настроек и данных о загруженности колл-центра);  
* показывает персонализированные проценты по депозитам для аутентифицированных пользователей интернет-банка;  
* аутентифицированным пользователям интернет-банка предоставляет информацию: есть ли у него заявки на депозит, которые уже созданы, но ещё не обработаны;  
* принимает заявку на открытие депозитов из интернет-банка (сбрасывает заявку в Kafka-очередь, обрабатывает в отдельном процессе);  
* принимает обновления информации о персонализированных ставках по депозитам для клиентов  (от процесса расчёта ставок по депозитам).

Сервис предлагается разрабатывать на Spring Boot, на языках Java/Kotlin  
В качестве внутренней БД предлагается использовать Oracle или Postgres.

### Процесс репликации данных в аналитическую БД

* Процесс нужен для последующего массового скоринга клиентов по депозитам (расчёт ставок по депозитам для вс)  
* Процесс запускается на airflow в 02:00 МСК, когда БД АБС сравнительно слабо нагружена.  
* Процесс перегружает инкремент данных за прошедшие сутки по всем клиентам из АБС в аналитическую БД, чтобы массовые процессы анализа данных (расчёт персонализированных ставок по депозитов, предварительный кредитный скоринг и др.) можно было вести без обращения к БД АДС.

Какие данные потребуются для массового скоринга по депозитам – мы не знаем, так что считаем, что копировать в аналитическую БД нужно всё, что есть в АБС.

Предлагается развернуть ещё одну базу Oracle и туда сбрасывать инкремент данных АБС. Oracle предоставляет для этого штатные средства переноса данных между БД с минимальной нагрузкой на исходную базу (Oracle GoldenGate и Oracle Data Guard)

### Процесс расчёта персональных ставок по депозитам

Процесс запускается в airflow по окончании репликации данных из БД АБС в аналитическую БД.  
Процесс рассчитывает:

- актуальные ставки по депозитам без персонализации (на основании актуальной ставки рефинансирования ЦБ РФ и макроэкономических показателей банка);  
- актуальные персональные ставки по депозитам для существующих клиентов банка, с учётом их накоплений, кредитов и транзакций и другой информации.

## Логика проектирования

При проектировании системы я обращал внимание на следующие ограничения:

* не перегрузить АБС;  
* не вносить изменений в код самой АБС (чтобы исключить повреждение банковских данных);  
* не заниматься разработкой нового функционала на устаревающих языках и фреймворках (PHP, [ASP.NET](http://ASP.NET) 4.5);  
* не перегружать систему кредитного скоринга массовыми расчётами в рабочие часы;  
* обеспечить асинхронную обработку заявок на депозиты и заявок на обратные звонки.

## Недостатки, ограничения, риски выбранного решения

### Риск: копирование данных из АБС в аналитическую БД может быть долгим

Неизвестно, сколько времени будет занимать копирование инкремента данных за прошедшие сутки из базы АБС в аналитическую БД.

Идеальный сценарий: это происходит за 2-3 часа, после чего сразу же запускается расчёт персонализированных ставок по депозитам, персонализированные ставки обновляются до начала следующего рабочего дня по европейской РФ.

Допустимый сценарий: инкремент данных происходит в течение ночи, после чего запускается расчёт персонализированных ставок по депозитам. Загрузка персонализированных ставок по депозитам в сервис депозитов будет происходить достаточно быстро, её можно делать даже в середине рабочего дня.

### Риск: Oracle может тормозить при аналитических запросах

Процесс расчёта персонализированных депозитов может занимать долгое время (более 8-12 часов), если Oracle будет тормозить на массивных аналитических запросах. Для таких задач обычно используют специальные аналитические БД вроде Clickhouse, но у нас с ним никто не работал. Пока попробуем Oracle, а если будет тормозить очень уж сильно, то тогда будем экспериментировать с Clickhouse (скорее всего, не придётся).

### Прочие недостатки

* требуется развёртывать сразу несколько дополнительных процессов и сервисов,  
* надёжность работы будет зависеть от стабильной работы kafka;  
* нужно усиливать devops-команду (если в банке таковая имеется).

# Альтернативы

## Рассчитывать депозитные ставки внутри АБС

Был вариант: не выделять отдельную аналитическую БД, не копировать туда данные по истории клиентов, а рассчитывать актуальные ставки по депозитам для клиентов внутри АБС, с помощью хранимых процедур на PL/SQL.

Но: по условию задачи, БД АБС и так перегружена.  
Но: по требованиям надёжности, интернет-банк должен быть доступен 24/7, с временем простоя не более 1/1000.

Если сервис депозитов или бэкэнд интернет-банка будет обращаться к АБС за актуальной ставкой для клиента каждый раз, когда клиент открывает страницу депозитов в интернет-банке, то мы будем ещё сильнее перегружать БД АДС в горячие часы.

Если делать массовый перерасчёт персональных ставок по депозитам для всех клиентов вне рабочего дня, то есть немалый шанс, что при массовых запросах БД АБС будет совсем недоступна, хотя бы и в ночное время, и мы не уложимся во время простоя 1/1000.

## Сервис депозитов как подсистема монолитного бэкэнда интернет-банка

Был вариант: реализовывать сервис депозитов как подсистему существующего монолитного бэкэнда интернет-банка.

Плюсы:

- хорошая производительность (если верить синтетическим бенчмаркам);  
- не нужно дополнительных усилий по развёртыванию нового сервиса.

Минусы:

- не поддерживает kafka (если верить тому, что написано в задании);  
- не поддерживается с 2022 года (т.е. всё равно надо переползать на ASP.NET Core – или уже на что-то более современное);  
- обновление ядра системы привязано к подрядчику, т.е. трудно оперативно вносить изменения.

Учитывая требования поддерживаемости кода – разрабатывать новый функционал на явно устаревшем фреймворке не стоит.

Кроме того, учитывая требования быстрого внесения изменений, если обновление системы привязано к внешнему подрядчику, то это не наш выбор.

## Сервис депозитов в виде микросервиса на FastAPI

Плюсы:

- FastAPI отлично подходит для быстрой разработки прототипов, особенно когда API часто меняется;  
- Производительность и скорость сравнимы с таковой у Spring Boot (всего в 1.5-2 раза хуже): [https://www.travisluong.com/fastapi-vs-fastify-vs-spring-boot-vs-gin-benchmark/](https://www.travisluong.com/fastapi-vs-fastify-vs-spring-boot-vs-gin-benchmark/)

Минусы:

- в банке никто на нём не пишет.

Соответственно, существующие разработчики банка не смогут ни быстро подключиться к разработке нового микросервиса, ни помочь в найме новых разработчиков в команду разработки новых микросервисов.
