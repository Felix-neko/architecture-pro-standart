Часть процессов для кредитной системы должна быть разработана ещё не этапе MVP (по условию задания 2):

* процесс копирования данных из АБС в аналитическую базу;  
* процесс массового кредитного скоринга для генерации персональных предложений по кредитам.

Основной микросервис кредитной системы тоже должен был появиться ещё на этапе MVP, хотя и с меньшим функционалом (только показ предложений по кредитам и отправка кредитной заявки в кредитный конвейер для дальнейшей обработки по старому процессу).

Но: чтобы было понятно, как работает система, мне придётся упоминать в этой доке и функционал с MVP-этапа.

# Решение

Микросервис работы с кредитами в итоге должен поддерживать следующую функциональность:

* вернуть актуальную информацию по стандартным кредитным предложениям от банка (для посетителей сайта без регистрации);  
* вернуть формат кредитной анкеты для выбранного кредитного предложения;  
* вернуть персональные предодобренные кредитные предложения для авторизованного клиента интернет-банка;  
* принять заявку на кредит от посетителя сайта;  
  * при создании заявки сразу провести экспресс-проверку заявки на системе онлайн-скоринга и вернуть её статус заявителю;  
  * отправлять заявителю уведомления по нескольким каналам: SMS \+ email (всегда) \+ заказ звонка через колл-центр (если заявка одобрена).  
* принять заявку на кредит от авторизованного клиента интернет-банка:  
  * при создании заявки – также провести экспресс-проверку заявки на системе онлайн-скоринга и показать её статус заявителю;  
* показывать клиенту интернет-банка созданные им кредитные заявки, находящиеся в обработке или ожидающие зачисления средств;  
* показывать клиенту интернет-банка информацию о взятых им кредиитах, которые он ещё не выплатил;  
* поддерживать поиск информации о персональных кредитных предложениях для клиента на стороне сотрудника колл-центра или отделения банка.

Сервис разрабатывается на Java/Kotlin Spring Boot.

Этот сервис должен был появиться ещё на этапе MVP, но на этапе MVP он должен был только показывать предложения по кредитам (стандартные и предодобренные персональные)

Также должны быть следующие airflow-процессы:

* \[должен остаться от MVP\] Процесс копирования данных из АБС в аналитическую БД  
* \[должен остаться от MVP\] Процесс массового кредитного скоринга для клиентов банка (выполняется по расписанию раз в сутки, генерирует актуальные персональные предложения по кредитам для всех клиентов банка).  
*  Процесс копирования инкремента данных с информацией о кредитах из БД АБС в отдельную БД с информацией о кредитах. Копировать нужно только некоторые таблицы – и только инкремент данных, с использованием штатных средств Oracle, так что есть шанс делать это чаще, чем 1 раз в сутки – и при этом не перегрузить БД АБС.

Также предлагается доработать следующие подсистемы:

* фронтэнд интернет-банка  
* фронтэнд сайта  
* \[вероятно\] сервис онлайн-скоринга кредитных заявок  
* кредитный конвейер, чтобы он отправлял кредитному сервису сообщения об изменении статуса заявок:  
  * что заявка отклонена  
  * что заявка принята  
  * что заявка отправлена на исполнение

## UC-1: заявка на кредит через сайт

### Действующие лица или системы

* Посетитель сайта  
* Фронтэнд сайта  
* Система колл-центра  
* Сотрудник колл-центра  
* Кредитный сервис  
* Сотрудники бэк-офиса  
* Кредитный конвейер  
* Система онлайн-скоринга кредитных заявок  
* БКИ и другие реестры  
* БД онлайн-аналитики  
* SMS-шлюз

### Описание

* Посетитель сайта открывает на сайте страницу кредитных предложений и просматривает там информацию об актуальных кредитных предложениях (без персонализации).  
* Посетитель кликает на выбранный тип кредита и заполняет кредитную анкету (для разных типов кредита анкета может быть разной).  
* Посетитель кликает на кнопку “Отправить анкету” и проходит SMS-подтверждение своего телефонного номера.  
* После успешного SMS-подтверждения клиент видит модальное окно что заявка c ID таким-то создана и ожидает предварительного скоринга (не закрывайте окно).  
* Дальше в течение 1 минуты для пользователя возможны варианты:  
  * заявка автоматически отклонена (отображено на экране \+ сообщение на email \+ SMS об отклонении заявки);  
  * заявка автоматически принята (отбражено на экране \+ сообщение на email \+ звонок из колл-центра);  
  * заявка рассматривается сотрудниками кредитного отдела бэк-офиса (отображено на экране \+ сообщение на email \+ SMS “Ваша заявка рассматривается специалистами, ответ ожидается в течение 1 рабочего дня”);  
    * если заявку отклонили, то email \+ SMS об отклонении заявки;  
    * если заявку приняли, то email \+ SMS \+ звонок из колл-центра о том, что заявка принята.

Под капотом происходит следующее:

* фронтэнд сайта запрашивает получает стандартный список кредитных предложений у кредитного сервиса;  
* формат полей для кредитной анкеты для выбранного кредитного предложения сайт также загружает с кредитного сервиса;  
* после создания заявки кредитный сервис отправляет заявку в кредитный конвейер;  
* кредитный конвейер запрашивает сервис онлайн-скоринга кредитов (предварительный онлайн-скоринг);  
* сервис онлайн-скоринга кредитов:  
  * делает поиск по паспортным данным заявителя, не является ли он уже клиентом банка, если является – то поднимает его историю из базы онлайн-аналитики;  
  * запрашивает внешние реестры данных (БКИ, по необходимости могут быть подключены ЕФРСУ, ФМС, ЕГРИП и др.);  
  * выставляет по данным анкеты и реестров предварительную оценку кредитного скоринга;  
  * выставляет флаги: автоотказ / автоприём / требуется подтверждение специалиста.  
* после предварительного скоринга КК отправляет кредитному сервису сообщение о том, чем закончился предварительный скоринг, чтобы кредитный сервис сообщил это клиенту (экран \+ email \+ SMS в случае отказа, экран \+ email \+ SMS \+ звонок из колл-центра в случае одобрения) или сообщил пользователю, что кредитная заявка рассматривается (в случае, если заявку будет смотреть специалист).  
* если заявку рассматривал специалст бэк-офиса, то он выставляет результат рассмотрения в кредитном конвейере, после чего результат КК тоже отправляет заявку в кредитный сервис, чтобы клиент получил email+SMS об отклонении или email+SMS+звонок о подтверждении.

## UC-2: Просмотр персонализированных предложений по кредитам в интернет-банке

### Действующие лица или системы

* Клиент банка  
* Фронтэнд интернет-банка  
* Кредитный сервис  
* БКИ и другие реестры  
* Процесс переноса данных из АБС в БД офлайн-аналитики  
* Процесс офлайн-скоринга предодобренных кредитов  
* БД офлайн-аналитики

### Описание

Клиент заходит в интернет-банк в панель “Кредиты” и видит там:

* актуальные стандартные кредитные предложения;  
* персонализированные предодобренные предложения для него.

Под капотом происходит следующее:

* каждую ночь по расписанию запускается airflow-процесс перенос инкремента данных из БД АБС в БД офлайн-аналитики;  
* после переноса данных в БД офлайн-аналитики запускается airflow-процесс офлайн-скоринга кредитов:  
  * рассчитываются стандартные проценты по различным типам кредитов для тех, кто раньше не пользовался услугами банка.  
  * для всех существующих клиентов генерируются предодобренные предложения по различным типам кредитов (со сроком и суммой);  
  * по окончании расчёта происходит обновление кредитного сервиса, чтобы он обновил данные в своей базе (через вызов специального эндпоинта в его REST API);  
* при вызове этого эндпоинта кредитный сервис обновляет свою БД (в отдельном процессе, батчами, асинхронно), после чего сбрасывает кэши кредитных предложений.

## UC-3: Оформление кредита в интернет-банке

### Действующие лица или системы

* Клиент  
* Фронтэнд интернет-банка  
* Кредитный сервис  
* БКИ и другие реестры  
* БД онлайн-аналитики  
* Процесс переноса данных из БД АБС в БД онлайн-аналитики  
* SMS-шлюз

### Описание

* Клиент кликает на заинтересовавшее его кредитное предложение и выбирает конкретную сумму и срок кредита.  
* Если нужно, вводит дополнительные данные для кредитной анкеты (для разных типов кредита форма такой анкеты может отличаться).  
* После этого клиент проходит SMS-подтверждение (в качестве ПЭП на взятие кредита).  
* После этого клиент видит поп-ап, что заявка создаётся и проходит предварительную обработку (в течение 1 минуты).  
* Дальше возможны варианты:  
  * заявка автоматически отклонена (поп-ап об отклонении заявки \+ SMS \+ email);  
  * заявка автоматически принята (поп-ап о подтверждении заявки \+ SMS \+ email);  
  * заявка рассматривается специалистами банка (поп-ап о том, что заявка создана и рассматривается \+ SMS \+ email).

* Под капотом происходит следующее:  
* фронтэнд интернет-банка запрашивает получает список кредитных предложений для пользователя  
* формат полей для кредитной анкеты для выбранного кредитного предложения сайт также загружает с кредитного сервиса;  
* после создания заявки кредитный сервис отправляет заявку в кредитный конвейер;  
* кредитный конвейер запрашивает сервис онлайн-скоринга кредитов (предварительный онлайн-скоринг);  
* сервис онлайн-скоринга кредитов:  
  * поднимает историю клиента из базы онлайн-аналитики;  
  * запрашивает внешние реестры данных (БКИ, по необходимости могут быть подключены ЕФРСУ, ФМС, ЕГРИП и др.);  
  * выставляет по данным анкеты и реестров оценку кредитного скоринга;  
  * выставляет флаги: автоотказ / автоприём / требуется подтверждение специалиста;  
  * NB: если кредит оформлялся по предодобренной заявке, то он может рассматриваться по упрощённой схеме, но какая-то часть заявок (в том числе все заявки на крупные суммы) всё равно будет дополнительно рассматриваться человеком.  
* после скоринга КК отправляет кредитному сервису сообщение о том, чем закончился предварительный скоринг, чтобы кредитный сервис сообщил это клиенту (поп-ап интернет-банка \+ email \+ SMS в случае отказа, поп-ап интернет-банка \+ email \+ SMS \+ звонок из колл-центра в случае одобрения) или сообщил пользователю, что кредитная заявка рассматривается (в случае, если заявку будет смотреть специалист).  
* если заявку рассматривал специалист бэк-офиса, то он выставляет результат рассмотрения в кредитном конвейере, после чего результат КК тоже отправляет заявку в кредитный сервис, чтобы клиент получил уведомление в интернет-банке (а также SMS \+ email \+ звонок в случае подтвержедния).  
* Платёжное поручение в на зачисление средств по кредиту по-прежнему уходит в АБС от кредитного конвейера раз в сутки, отдельным процессом, но анализ структуры нагрузки на БД АБС и возможность её масштабирования я в эту задачу не включал.

## UC-4: просмотр информации о своих кредитах и заявках в интернет-банке

### Действующие лица или системы

* Клиент  
* Фронтэнд интернет-банка  
* Кредитный сервис  
* АБС  
* БД кредитов и платежей  
* Процесс экспорта информации о кредитах и платежах из АБС

### Описание

Клиент заходит на панель “Кредиты” в своём интернет-банке и видит там:

* информацию о своих заявках на кредиты, которые ещё рассматриваются специалистами (чтобы он не насоздавал заявок-дублей по 2-3-4 раза);  
* информацию о своих заявках на кредиты, которые были одобрены и по которым ожидается зачисления средств со стороны банка;  
* информацию о тех кредитах, которые он брал, но ещё не выплатил (сумма, сроки, данные о графиках платежа и др.).

Данные по кредитам и платежам для клиентов есть в БД АБС, но работать с ней напрямую нам запрещено, чтобы её не перегружать.  
Нужен дополнительный airflow-процесс по расписанию, который будет экспортировать инкрементальные данные по кредитам и платежам из АБС в БД кредитов и платежей с которой будет работать кредитный сервис. Процесс экспорта будет работать регулярно (для начала 1 раз в сутки по ночам, в перспективе – раз в час, если удастся сделать его не слишком тяжёлым для АБС).

# Альтернативные решения

## Оставить только онлайн-скоринг

Запускать его каждый раз, когда клиент смотрит предложения по кредиту, кэшируя на какое-то время.

### Плюсы

Не нужно писать отдельный скоринговый процесс.  
Пока активных пользователей интернет-банка мало, может работать достаточно быстро.

### Минусы

По условию задания, система скоринга и так перегружена в рабочие часы, когда пользователей интернет-банка станет больше, это её убьёт.

## Добавить API Gateway и делать канареечные релизы

### Плюсы

Это может уберечь систему от многих падений и убрать многие же репутационные риски, для банка это очень важно.

### Минусы

* Найм девопсов займёт какое-то время.  
* У “архитектора” горят дедлайны по сдаче, и расписать и разрисовать применение API Gateway и канареечных релизов на этом проекте он уже не успевает.

Предлагаю считать, что в боевом проекте – применение API Gateway и переход на канареечные релизы для новой функциональности будет описано в отдельном ADR, который будет выпущен уже после старта реализации MVP, в процессе найма первых девопсов.
